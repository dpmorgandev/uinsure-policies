# inv-003: F6 docs state claims the repo does not prove
## Question
Why does the reviewer FAIL build/F6 at attempt 2 (A2), and is each cause in the docs' sources, the builder's method, or the orchestrator's briefs?
## Hypothesis
The builder carried statements over from secondary sources (QA notes, the first long draft) without checking each
claim against the code, and the orchestrator's briefs asked for numbers to be checked but not causal or control
claims, and never said to drop author-facing notes and internal finding ids. Disproved if the claims were checked
against code, or if the briefs required that.
## Evidence
- docs/trace/build/F6/verdicts/A2-reviewer.json: FAIL, P1 R1 (design.md states a JSON-naming-policy cause for the ?REFERENCE key that the code contradicts), P2 R2-R4
- docs/trace/build/F6/verdicts/A2-security.json: PASS, P2 S1 (no internet-exposure statement), S2 (forwarded-header caveat missing from design.md)
- docs/qa/build-F2.md: the ?REFERENCE cause began as a guess ("That looks like…"), then the F2 sign-off row and the F2 snapshot stated it as fact
- docs/plans/active/build.dag.yaml F6 t1 title: tells the builder to state the camelCase/?REFERENCE claim, frames items "for David's review", names internal finding ids
- docs/trace/build/F6/activity.jsonl: one builder took causes from QA and verdict notes; the rewrite builder read no code before writing all three docs; the A1 fix read no code
- docs/trace/build/F6/loop.jsonl: the F6 gates check links, URLs, build, tests and scope, nothing about claims
## Findings
Yes. The cause is in all three places, and one missing step ties them together.
Findings: [findings/A2.md](../../trace/build/F6/findings/A2.md).
- I1 (R1, new): docs/design.md:64-65 states an unproven cause for the ?REFERENCE key; the repo proves the 400, not the key's casing or its cause (sources hardened a QA guess; the brief asked for it; the builder copied it).
- I2 (new): "validation error keys are camelCase" overclaims; ValidationProblems.cs:25-26 only lower-cases each segment's first letter.
- I3 (R2): design.md:50 widens requirements.md:121 from "every rule violation" to "every problem"; the same class as A1 I4, fixed one line lower but not here.
- I4 (R3): infrastructure/README.md:110 "only merged code reaches them", copied from an F5 security note; no branch control exists.
- I5 (R4): author-facing notes and internal ids in assessor docs, from the brief.
- I6 (S1), I7 (S2), I8: no exposure statement; forwarded-header and "never reached" runtime claims untested on App Service.
- I9-I13 (new, unflagged): an inverted pool-per-environment rationale; an unconditional "cannot administer"; an unpinned enum-case claim; a merge-commit guarantee the repo can't enforce; "bounded only by" the write rate.
- I14 (method, recurring across A1 and A2): no step traces each factual sentence to a file:line, test or measurement, so each round fixed only its cited lines. Hypothesis confirmed with two corrections: the guess was already stated as fact in the F2 records before F6, and R2 came from widening a requirement, not a QA note. The brief's exact text can't be cited (dispatch prompts aren't in the trail).
