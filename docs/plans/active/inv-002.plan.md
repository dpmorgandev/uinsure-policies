# inv-002: F5 what-if still precedes the prod approval
## Question
Why does the reviewer FAIL build/F5 at attempt 2 (A2.4), and is each cause in the infrastructure, the checker, or the orchestrator's briefs?
## Hypothesis
The orchestrator's fix brief for the QA what-if defect specified "two jobs in one stage", on a wrong model of
Azure DevOps (environment checks are evaluated before a stage starts, for every resource it uses); the builder
followed the brief and the red checker encoded the same model, so no gate could catch it. Disproved if approvals
are evaluated per job, if the builder deviated from the brief, or if the brief asked for a separate stage.
## Evidence
- docs/trace/build/F5/verdicts/A2.4-reviewer.json: FAIL, P1 R1 (approval still precedes the what-if), P1 R2 (checker asserts job-level separation only), P2 R3 (QA line references stale)
- docs/trace/build/F5/verdicts/A2.4-security.json: PASS, P2 S1 (the unapproved what-if uses the full subscription-scope ARM connection)
- docs/qa/build-F5.md observation O1: located the defect at stage start and named a what-if-only stage
- docs/trace/build/F5/loop.jsonl gate.qa (925fe90): restated O1 at job level ("inside the deployment job")
- docs/trace/build/F5/activity.jsonl: the red and green builders edited without reading O1; both commit subjects say "in its own job"
- infrastructure/pipelines/stage-template.yml at c2af74d: WhatIf job and the policies-<env> deployment job in one stage, Deploy_<env>
- infrastructure/pipelines/check-pipeline.py: stage lookups by index (stages[0]) in four places; no stage-level assertion
## Findings
Yes: the cause is upstream of the builders, in how the orchestrator handed on the QA defect, and it carried into
both the infrastructure and the checker. Findings: [findings/A2.4.md](../../trace/build/F5/findings/A2.4.md).
- I1 (R1, new): stage-template.yml:15-56 puts the what-if job in the stage that consumes environment policies-<env>; checks run at stage start, so the prod approval precedes the what-if. The comment at :19-21 is false.
- I2 (R2, new): check-pipeline.py:62, :76-86 assert job-level separation; :62-63, :153, :181 hard-code stages[0]; the stage schema allows a condition that could bypass the order. Red, green and the mutation proof all encoded the brief's model.
- I3 (R3, new): docs/qa/build-F5.md cites pre-fix lines; the in-task QA route has no step that re-runs the script against the fixed head.
- I4 (security S1, new): stage-template.yml:34 runs the unapproved what-if on the deploy connection with subscription write rights; an approval check on that connection would gate the what-if stage and bring the defect back.
The exact brief text can't be cited: dispatch prompts are not recorded in the trail.
